SessionManager为什么不需要单例模式?
  因为每个Activity都可以创建自己的SessionManager实例，而它们实际上共享同一个SharedPreferences文件。这样设计的好处是每个Activity可以独立管理自己的会话状态，但所有实例都指向同一个数据源。
SessionManager的工作原理：
```java
// SessionManager 不是传统意义上的"对象持久化"
// 而是基于 Android 系统的 SharedPreferences 机制
public class SessionManager {
    private SharedPreferences preferences;  // 这个才是真正的"数据库"
}
```
多个SessionManager的真相：
```java
// 在 MainActivity 中
SessionManager sessionManager1 = new SessionManager(this);

// 在 LoginActivity 中  
SessionManager sessionManager2 = new SessionManager(this);

// 这确实创建了两个不同的 SessionManager 对象！
// 但是它们访问的是同一个 SharedPreferences 文件
```

```plaintext

├── /data/data/com.liu.coursedesign/shared_prefs/
│   └── user_session.xml  ← 真正的数据存储位置

📱 应用内存中
├── MainActivity 
│   └── sessionManager1 实例 ────┐
│                              │ 
└── LoginActivity              │ 都指向同一个文件
    └── sessionManager2 实例 ────┘
```

>## 🔍 核心原因 (Core Reason)
>
>**文件路径 (File Path) vs. 内容URI (Content URI)**
>
>- **`KnowledgeAdapter` 能行**：因为用户通过相册选择图片时，系统返回的 
>
>knowledge.getImagePath()
>
> 存储的是一个**内容URI (Content URI)**，例如 `content://com.android.providers.media.documents/document/image%3A12345`。
>- **`AdminAdapter` 失败**：因为 `new File("content://...")` 这样的操作是**无效的**。`java.io.File` 类只能理解标准的**文件系统路径** (例如 `/storage/emulated/0/Pictures/my_photo.jpg`)，它完全不认识 `content://` 这种协议。所以 
>
>imageFile.exists()
>
> 永远返回 `false`，导致代码直接跳转去显示占位图 
>
>ic_info

>
>---
>
>## 💡 深入解析 (In-depth Analysis)
>
>### 1. `AdminAdapter` 的问题：误解了“路径”的含义
>
>```java
>// ❌ 错误的代码逻辑
>String imagePath = knowledge.getImagePath(); // 假设这里得到的是 "content://..."
>File imageFile = new File(imagePath);        // 创建了一个无效的文件对象
>if (imageFile.exists()) {                    // 这里永远是 false！
>    // ... 这段代码永远不会执行
>} else {
>    // 总是执行这里，显示文件不存在的占位图
>    ivThumbnail.setImageResource(R.drawable.ic_info);
>}
>```
>
>- **File (文件)**: 这是Java标准库中的一个类，用于表示文件系统中的一个文件或目录。
>- **Path (路径)**: `File` 类期望的路径是操作系统能直接识别的，比如Windows的 `C:\Users\..` 或Linux的 `/home/...`。
>- **exists (存在)**: 这个方法会去文件系统中检查这个路径是否真实存在一个文件。对于 `content://` 这样的字符串，文件系统里没有对应的文件，所以检查必然失败。
>
>把**内容URI**想象成一个**邮政信箱地址**。您知道信箱号码，可以给它寄信（通过`ContentResolver`），但您不能直接开车到那个“地址”，因为它不是一个物理位置。而**文件路径**就像一个**家庭住址**，您可以直接开车过去。
>
>### 2. `KnowledgeAdapter` 的成功：Glide的“智能”
>
>```java
>// ✅ 正确的代码逻辑
>Glide.with(context).load(knowledge.getImagePath()).into(imageView);
>```
>
>- **Glide (滑行)**: 这个库的名字寓意着像滑行一样平滑、流畅地加载图片。它是一个非常智能的**图片快递员**。
>- **load (加载)**: 当您调用 `.load()` 方法并把 
>
>imagePath
>
> 字符串传给它时，Glide内部会做一系列智能判断：
>    1.  **“这是个网址吗？”** (Is it a URL?) - 检查是否以 `http://` 或 `https://` 开头。
>    2.  **“这是个文件路径吗？”** (Is it a file path?) - 检查是否以 `/` 开头，指向本地文件。
>    3.  **“这是个Android资源吗？”** (Is it an Android resource?) - 检查是否是一个`Integer`类型的资源ID。
>    4.  **“这是个内容URI吗？”** (Is it a Content URI?) - 检查是否以 `content://` 开头。
>
>当Glide发现这是一个**内容URI**时，它知道不能用 `new File()`。它会转而使用Android系统的 **`ContentResolver` (内容解析器)** 去向对应的**`ContentProvider` (内容提供者)** 请求图片数据流。这个过程对您是完全透明的。
>
>**简单来说：您把任何“地址”（网址、文件路径、内容URI）给Glide，它自己会想办法把“快递”（图片）送到您的 `ImageView` 手中。**
>

>

>imagePath

>
> 
>
> notifyDataSetChanged()
>
>  被Android Studio标记为不推荐的原因主要有：
>
> ### 1. **性能问题 (Performance Issues)**
> - **全量刷新**：这个方法会强制RecyclerView重新渲染**所有可见的item**
> - **无差异更新**：即使只有一个item发生变化，整个列表都会重新绘制
> - **动画丢失**：无法提供流畅的插入、删除、移动动画效果
>
> ### 2. **用户体验差**
> - 列表会出现明显的"闪烁"效果
> - 滚动位置可能会丢失
> - 没有视觉反馈告诉用户具体哪里发生了变化
>
> ## 更现代的解决方案
>
> ### 方案一：使用 `DiffUtil`（推荐）
>
> ```java
> public void updateData(List<Knowledge> newKnowledgeList) {
>     // 使用DiffUtil计算差异 (calculate differences)
>     DiffUtil.DiffResult diffResult = DiffUtil.calculateDiff(
>         new KnowledgeDiffCallback(this.knowledgeList, newKnowledgeList)
>     );
>     
>     // 更新数据源 (update data source)
>     this.knowledgeList = newKnowledgeList;
>     
>     // 应用差异更新 (apply differential updates)
>     diffResult.dispatchUpdatesTo(this);
> }
> 
> // 创建DiffCallback类 (create diff callback class)
> private static class KnowledgeDiffCallback extends DiffUtil.Callback {
>     private final List<Knowledge> oldList;
>     private final List<Knowledge> newList;
>     
>     public KnowledgeDiffCallback(List<Knowledge> oldList, List<Knowledge> newList) {
>         this.oldList = oldList;
>         this.newList = newList;
>     }
>     
>     @Override
>     public int getOldListSize() {
>         return oldList.size();
>     }
>     
>     @Override
>     public int getNewListSize() {
>         return newList.size();
>     }
>     
>     @Override
>     public boolean areItemsTheSame(int oldItemPosition, int newItemPosition) {
>         // 比较item的唯一标识 (compare unique identifiers)
>         return oldList.get(oldItemPosition).getId() 
>             == newList.get(newItemPosition).getId();
>     }
>     
>     @Override
>     public boolean areContentsTheSame(int oldItemPosition, int newItemPosition) {
>         // 比较item的内容是否相同 (compare if content is the same)
>         Knowledge oldKnowledge = oldList.get(oldItemPosition);
>         Knowledge newKnowledge = newList.get(newItemPosition);
>         return oldKnowledge.equals(newKnowledge);
>     }
> }
> ```
>
> **DiffUtil的工作原理**：
> - **Diff Algorithm（差异算法）**：计算两个列表之间的最小变化
> - **Selective Updates（选择性更新）**：只更新实际发生变化的item
> - **Animation Support（动画支持）**：自动提供插入、删除、移动动画
>
